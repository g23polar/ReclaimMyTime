# M1+M2 gate — 2026-11-15

Run as a `tessl code review` lens over 9a3ea30..HEAD.

## Judgement
The scheduling and confirmation paths contain three verified correctness issues: repeated block moves retain obsolete pins, replacement-week solves can omit finished effort, and confirmation can promote a proposal for a week that has already ended.

## Findings

### [major] Moving a pinned block again retains its previous placement — server/app/api/blocks.py:80

`patch_block` stages a fresh `pin_added` for every edit without removing the constraint responsible for the block's current placement. After confirming one move, moving the resulting future block to another valid, disjoint slot leaves both pins in the solver input. `_place_pins` realizes both, minting another lineage when the original is already used, so confirmation retains an unwanted session rather than moving it and can schedule more effort than the project requires. Repeated edits must replace the prior placement constraint for that session while keeping both changes subject to proposal and confirmation semantics.

### [major] Replacement-week solves omit ended work outside the new horizon — server/app/db/solver_io.py:615

`build_solver_input` loads frozen blocks only where they overlap the replacement horizon, while `completed_minutes` credits only rows already marked `completed`. On Tuesday, changing the week start from Monday to Tuesday therefore omits Monday's ended but still `planned` deadline-project blocks if no intervening read has swept them. Neither proposal nor the confirmation stale check performs that sweep before solving. The supersedability guard allows these ended blocks, and confirmation marks them completed only after accepting the inflated schedule, leaving excess work in the new live plan. Ended, non-skipped effort outside the replacement horizon must be credited before computing and validating the replacement, independently of prior reads.

### [major] Confirmation can promote a proposal for an expired week — server/app/db/write_paths.py:1074

Confirmation invokes `_stale_check` using the proposal's stored horizon but never verifies that it is still the current preference week. For an empty schedule, or a fully frozen schedule whose frozen set remains unchanged, re-solving the old horizon can compare equal after rollover. Confirmation then applies the staged mutations and promotes the old week's plan; `GET /plans/current` finds no plan covering the new week. The current-week validation at staging and the rollover fallback when a stale exception occurs do not protect this equal-schedule path. Rollover must be reconciled before mutations are applied, with the current week's replacement subject to review even when the old proposal has no remaining blocks.

## Verdict (main session)

Pass with conditions: the three majors are fixed before M3/M4 start.
